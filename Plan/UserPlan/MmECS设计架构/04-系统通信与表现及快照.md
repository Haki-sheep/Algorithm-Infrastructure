# 04 系统通信与表现及快照

本文约定 MmECS 首版采用纯 C# SparseSet 单线程固定 Tick。本章说明数据如何流动 哪些边界必须固定 以及以后怎样接入快照和引擎。首版计划聚焦 ECS 本身 不实现联网 预测 回滚同步或自动并行调度。具体实现进度以源码和实测为准。

## 1 先区分状态 意图 与结果

同一个游戏行为可能同时产生状态变化 请求和事件。不要因为它们都能携带数据 就把所有内容塞入同一种消息总线。

| 类型 | 回答的问题 | 例子 | 主要消费者 |
| --- | --- | --- | --- |
| Component | 当前是什么状态 | 当前生命值 位置 物品数量 | 模拟系统 |
| World 单例 | 整个 World 当前是什么状态 | 对局阶段 随机状态 全局计时 | 模拟系统 |
| Input | 某个 Tick 的持续控制是什么 | 移动方向 瞄准方向 按钮位 | 输入处理系统 |
| 业务 Command | 请求执行什么操作 | 装备物品 接受任务 使用技能 | 对应业务系统 |
| 内部请求 | 本次模拟还需要谁处理什么 | 伤害请求 掉落请求 | 指定后续系统 |
| Signal | 某件模拟事实已经发生 | 伤害已结算 | 显式注册的模拟处理器 |
| ViewEvent | 表现层需要呈现什么结果 | 飘字 播放命中特效 | 引擎适配与表现层 |

状态是权威结果 Command 只是意图。例如提交装备请求不代表装备成功 是否满足条件由模拟决定。

## 2 内部系统优先通过组件交换长期状态

移动系统写 Position 碰撞系统读 Position 这是最直接的数据依赖。Health Inventory QuestProgress 这类持续存在的信息应保存为组件。不要只发送一次事件 然后让另一个系统私下保存唯一有效的数值。

系统负责哪类字段 必须在实现前写清楚。例如 DamageSystem 结算生命变化 RegenSystem 负责回复 其先后顺序由 Scheduler 明确配置。如果两个系统都能改同一字段 顺序本身就是游戏规则的一部分。

首版调度使用明确的阶段和列表顺序。不通过反射扫描顺序 字典枚举顺序或订阅先后来推导业务顺序。暂时不实现读写依赖推导与多线程。

## 3 内部请求队列解决分阶段处理

请求表示生产者已经收集了信息 但尚未由负责系统处理。例如 HitSystem 产生 DamageRequest DamageSystem 统一消费并写入 Health。这种方式让命中检测与伤害规则各自集中。

DamageRequest 至少描述目标 伤害来源 伤害参数以及顺序信息。目标用 Entity 句柄表示 不存 Unity 对象或某个组件行的引用。如果处理规则需要命中瞬间的位置 请求应复制该位置。

首版对每种请求规定唯一消费阶段。生产者必须排在消费者前面 消费后清空该阶段对应队列。队列中的顺序是显式规则 不能偶然依赖散列表枚举。

| 队列 | 生产阶段 | 消费阶段 | 生命周期 |
| --- | --- | --- | --- |
| DamageRequest | 命中检测 | 伤害结算 | 当前 Tick |
| LootRequest | 死亡结算 | 掉落计算 | 当前 Tick |
| SpawnResult | 上一 Tick 的结构提交 | 当前 Tick 约定的生成结果处理系统 | 消费前属于模拟状态 |
| FutureAction | 当前 Tick 的任意已约定阶段 | 明确的未来 Tick | 消费前属于模拟状态 |

排在消费者之后的系统 不得继续向当前 Tick 已消费的队列追加请求。需要延后时必须写入明确标注目标 Tick 的未来队列。未消费请求不能在 Tick 末尾默默丢弃 也不能默默留到下一 Tick。

## 4 Signal 是可选机制 首版可以先不做

Signal 表示模拟内部已经发生的事实。适合让少量明确的规则响应同一事实 例如伤害结算后增加受击计数。

若首版增加 Signal 本文建议使用显式处理器列表与固定调用顺序。直接调用的 Signal 在发出点执行 处理器属于当前模拟步骤。它不是独立线程 也不是可以任意延后的任务。

不要允许处理器重入同一种 Signal 或重新启动 Simulation.Tick。Signal 内依然遵守组件读写归属与结构变更边界。如果处理器需要晚些处理 应追加到规定阶段的请求队列。

Signal 不替代持久状态。Signal 也不直接调用 UI 播放音效或操作 GameObject。MmECS 首版用组件与请求队列即可完成完整业务 再按实际重复需求增加 Signal。

## 5 结构命令和业务 Command 是两层东西

业务 Command 表达行为意图 例如 UseItem。结构命令表达 ECS 存储操作 例如 CreateEntity AddComponent DestroyEntity。

UseItem 可以只减少已有组件的数量 也可以追加销毁实体的结构命令。它们可能由一次行为连接起来 但不应共用语义不清的万能命令类型。

首版运行期每个 Tick 末尾只进行一次结构命令提交。系统查询过程中不得即时创建销毁实体或增删组件。已有组件中的普通字段可以即时修改 后续系统能读到更新值。

| 当前 Tick 的操作 | 当前 Tick 后续系统 | Tick 末提交后 |
| --- | --- | --- |
| 修改已有 Health.Current | 立即读到新数值 | 新数值保留 |
| 排队增加组件 | 查询不到新增组件 | 新组件进入存储 |
| 排队创建实体 | 查询不到新实体 | 新实体进入存储 |
| 排队销毁实体 | 仍可能查到实体 | 实体移除并更新代际 |

提交之后本 Tick 不再运行游戏系统 所以新增结构从下一 Tick 开始参与系统查询。不能为了让后续系统看到新增结构 就在系统之间偷偷增加提交点。

待销毁实体在本 Tick 仍然可能被查询到。需要屏蔽后续业务时 使用预先存在的 Lifecycle.PendingDeath 或 ScheduledDespawn 字段。不能临时追加 DeadTag 并假定当前 Tick 后续查询会立即排除它。

结构命令内部也需要保持明确的入队与回放顺序。同实体的冲突操作规则由核心存储章节统一定义 表现层不得参与裁决。

## 6 外部 Input 和业务 Command 如何进入模拟

Input 用于持续控制 业务 Command 用于离散意图。例如按住方向键是 Input 点击装备按钮是 EquipItemCommand。一次点击不能因为渲染了三帧 就生成三次装备操作。

输入适配器把引擎输入转换成普通 C# 数据。数据记录目标 Tick 玩家或控制对象以及需要的参数。同一 Tick 多条业务 Command 必须有稳定的顺序编号。

外部句柄在入口验证 WorldId 与 StateEpoch 后转换为模拟 Entity 再进入模拟队列 队列不保留宿主 Epoch。命令序号由 World 拥有的分配器统一分配 并与未来队列一起保存恢复。目标在真正消费时是否仍有效由相应业务规则判断。

恢复快照时保留快照内已经接纳的未来输入与命令 同时丢弃宿主侧尚未接纳的旧 Epoch 输入。新时间线的新输入使用恢复后的序号继续分配 不能把快照内合法命令当作旧宿主消息拒绝。

首版在 Tick 开始处冻结本 Tick 的输入与 Command 批次。本 Tick 执行过程中到达的外部意图 进入后续 Tick。模拟消费冻结批次后才运行约定的业务系统。

外部对象没有修改组件的入口。UI 可以立刻显示本地按钮反馈或等待状态 但不能直接扣背包 改金币或认定技能成功。

## 7 View 读取只读状态 接收自包含事件

表现层需要两类输出 当前状态与瞬时结果。当前状态用于显示血量 背包内容 角色位置等。ViewEvent 用于命中特效 飘字 音效等短暂反馈。

首版只在 World 完成当前 Tick 后向外开放只读读取。不把可写 ref 组件引用交给表现层。需要跨 Tick 保留的数据必须复制 不能缓存 SparseSet 内部行地址。

自包含 ViewEvent 应复制表现所需信息。例如命中特效事件包含目标句柄 命中位置 效果标识 伤害值以及发生 Tick。目标在 Tick 末销毁后 事件仍能在正确位置播放特效。不要只给一个 Entity 然后要求表现层临时回查已被删除的组件。

ViewEvent 可以引用表现资源的稳定标识。实际 Prefab AudioClip 材质等由引擎适配器映射。模拟核心无需知道这些引擎资源类型。

## 8 UI 打开先读当前值 事件只帮助刷新

背包面板打开时读取当前背包状态。生命条绑定目标时读取当前生命值。重新打开面板不能依赖它曾经接收过所有历史事件。

对于血量 背包等长期状态 界面变更事件只表示需要刷新。刷新时读取权威状态 或使用经过定义的只读展示投影。界面暂停 更新较慢或被销毁重建 都能由当前状态恢复显示。

为了降低读取量 可以在已存在的数据里维护变更版本。UI 记录上次看到的版本 有变化时重新读取。版本字段是否属于模拟状态 要按它会不会影响模拟规则明确决定。

选择标签页 滚动位置 鼠标悬停与窗口开关属于 UI 自己的状态。选中目标如果会影响技能结算 则应转换为输入或 Command 交给模拟。判断归属的标准是是否参与权威规则。

## 9 同 Tick 与跨 Tick 的事件清理边界

模拟内部请求在约定的消费阶段清空。给 View 的输出在 Tick 末提交完成后物化为独立批次。这两类队列不能共用一次 Clear。

一个渲染帧可能推进多个模拟 Tick。例如一次渲染前连续完成 Tick 20 和 Tick 21 表现状态可以只显示最新结果。但这两个 Tick 产生的命中特效不能因为共用一个临时列表而只剩后一批。

首版适配器按批次读取并确认已经消费的 ViewEvent。确认后释放对应输出批次 避免每帧重复播放。切场景或恢复快照时明确丢弃旧批次 并重新绑定当前状态。

只在某个 Tick 内有效的请求不得被 View 保存。仅用于表现的输出批次不属于决定未来模拟的状态。如果一个所谓表现事件还能反过来决定伤害 它实际属于模拟输入或内部业务。

## 10 World Frame 和引擎帧不要混用

World 拥有当前可变的模拟状态和 ECS 存储。WorldState 表示需要保存和恢复的纯模拟数据。存储缓存 查询缓存与调试统计独立管理 可重建缓存不成为唯一权威数据。

本文把某个已完成 Tick 的只读输出叫 StateFrame。它可以是投影或快照 不一定复制完整 World。引擎渲染帧则是 Unity 或 UE 的一次画面更新 两者频率可以不同。

World.Tick 表示已经完整提交的 Tick 初始值可以为零。执行下一步时 StepContext 使用目标 Tick World.Tick + 1。完成提交后 World.Tick 才更新为该目标 Tick。

Quantum 使用 Frame 承载模拟状态 但不应直接把这个名字等同于 Unity 渲染帧。MmECS 不必为了名称相似而提前实现历史帧缓存 预测帧或校验帧。

## 11 World 级单例属于各自 World

单例表示同一个 World 内只有一份该类型数据。例如 MatchState GlobalRules RandomState。它应由 World 实例持有 随对应 World 一起创建 恢复和销毁。

它不是 C# static 字段 也不是跨对局共享的全局服务。同时运行两个 World 时 它们必须拥有各自的计时 随机状态与对局阶段。只读配置可共享 但配置版本与初始化条件必须明确。

引擎资源加载器 日志输出器与展示对象池属于宿主服务。这些对象不能混入 World 的模拟单例并跟随快照复制。

## 12 快照必须覆盖所有决定未来的状态

首版只允许在 Tick 完整结束的边界生成快照。此时本 Tick Command 已消费 临时业务请求已消费 结构命令已回放。Tick 已推进 对外输出已物化 此后才允许下一 Tick 开始。

| 状态 | 为什么需要保存 |
| --- | --- |
| 活跃实体与组件数据 | 决定当前业务状态 |
| 实体分配器 代际 空闲槽与分配顺序 | 决定未来创建的身份和旧句柄有效性 |
| SparseSet 的实体行顺序 | 系统按存储顺序遍历时会影响未来处理顺序 |
| World 单例与 Tick | 决定全局规则与时间条件 |
| 随机源内部状态 | 决定后续随机序列 |
| 未来 Tick 的输入 Command 与延迟业务队列 | 已经安排但尚未执行的行为也会影响未来 |
| 待消费的 SpawnResult | 创建已落地 但申请方尚未处理实体关联 |
| 尚会影响后续排序的序号分配器 | 恢复后必须延续同一条顺序 |

Sparse 映射可以由保存的 Dense 顺序重建。但不能只保存组件值 然后随意改变恢复后的行顺序。若希望顺序不影响结果 必须先给所有相关规则定义稳定排序。

快照边界处结构命令队列应为空 因而无需把当前 Tick 已执行的命令重复保存。未来输入队列不能因为尚未进入当前 Tick 就被排除。只要系统实例私藏的可变字段会影响未来 就必须迁入明确的模拟状态或纳入快照。

## 13 恢复模拟后 View 必须重新对账

Entity 的索引与代际只能防止同一实体生命周期中的旧句柄误用。恢复旧快照后 同样的索引和代际可能再次出现 但外部仍留着另一条时间线的绑定。

宿主持有 WorldId 与 StateEpoch 作为引用隔离信息。WorldId 区分不同 World 会话 StateEpoch 在每次恢复或整体替换状态时更新。这两个信息不直接参与数值模拟 不从旧快照恢复成旧 Epoch。

View 绑定键由 WorldId StateEpoch Entity 共同组成。恢复时丢弃旧 Epoch 的输出与绑定 重新读取当前实体集合。实体外观与 UI 从恢复后的状态重建或重新匹配。只看 Tick 不足以隔离旧消息 因为恢复后可能再次运行相同 Tick。

普通恢复不自动重播已经展示过的音效和飘字。以后加入回滚表现时 再单独设计事件标识 确认与撤销规则。

## 14 引擎分离的实际边界

Unity 适配层负责输入采集 展示实例 动画 UI 插值与资源映射。这些职责通过输入接口与只读输出接口连接核心。核心程序集不引用 UnityEngine 也不需要知道 UI 框架的存在。

UE 默认不直接运行这套纯 C# 核心。真正复用时需要单独选择 C# 宿主 桥接或进程间方案。接口解耦能减少迁移成本 不能消除运行时接入成本。

如果引擎物理结果决定伤害 移动阻挡或落点 物理就参与权威模拟。带内部接触缓存与求解状态的物理系统不能被伪装成单纯 View。需要明确其状态如何保存 或明确通过输入记录与恢复策略管理该边界。

## 15 确定性 快照 存档与联网分别验收

快照解决保存并恢复当前模拟状态。确定性解决相同初始状态和输入 是否产生相同结果。长期存档还涉及格式版本 数据迁移与配置兼容。联网另外涉及传输 同步策略 延迟处理以及状态校验。

固定 Tick 是确定性设计的基础之一 但还需处理随机来源 遍历顺序 浮点差异与外部依赖。暂时不为可能联网而强制使用定点数。先完成同进程的保存 恢复 与继续运行一致性验证。

首版的行为验收包含 新增结构下一 Tick 可查询 待销毁实体本 Tick 被标记屏蔽。还包含 UI 中途打开能读对状态 连续多个 Tick 的表现事件不丢失。恢复后继续相同输入产生相同模拟结果 旧 Epoch 事件无法绑定新 View。

## 16 Quantum 3 参考只用于厘清概念

Quantum 的游戏事件用于从模拟向表现传递信息。其模拟内部机制与表现事件应分开理解。不要为了凑出四种方式 把单例 Frame 查询 输入 Command Signal 和 Event 强行放入同一层级。

官方把表现层获取模拟信息分成两类 查询游戏状态 与 Events/Callbacks。记忆中的四种可能是 Input Command Event Callback 但它们包含不同方向 不能确定这是某篇资料的原始分类。

| Quantum 概念 | 方向或归属 | 用途 |
| --- | --- | --- |
| Input | 外部进入模拟 | 持续控制输入 |
| Command | 外部进入模拟 | 离散操作意图 |
| Signal | 模拟系统之间 | 内部逻辑响应 |
| Event | 模拟到表现 | 瞬时表现反馈 |
| Callback | 框架到接入层 | 采集输入 游戏开始 更新 View 等时机 |
| 查询 Frame | 表现读取模拟 | 持续显示当前位置 血量等状态 |

Frame 中的单例属于状态组织 不构成第七种消息通道 Quantum Event 本身也不负责在客户端之间传输或同步数据。
