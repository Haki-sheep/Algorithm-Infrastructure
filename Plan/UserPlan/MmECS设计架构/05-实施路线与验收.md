# MmECS 实施路线与验收

本文把设计拆成可以逐步完成的小阶段 每阶段包含实现内容 学习重点与可观察的完成条件

下面的测试是各阶段的验收要求 实现状态以当前源码和真实测试结果为准

## 1 实施顺序

| 阶段 | 交付物 | 必须理解的内核 |
|---|---|---|
| A | Entity 与 World 分配器 | 身份 生命周期 回收与代际 |
| B | 一个泛型组件存储 | 稀疏定位 紧密遍历 删除回写 |
| C | Query 与最小 System 列表 | 多组件关联 数据依赖 执行顺序 |
| D | 固定 Tick 与结构缓冲 | 字段写入和结构变化的可见时间 |
| E | 战斗与 View 交互样例 | 请求 状态 瞬时事件的不同职责 |
| F | 同版本内存快照 | 完整状态与可重建缓存的边界 |
| G | 基准与调试能力 | 定位成本后再优化 |

前一个阶段的生命周期语义没有确定时 不继续堆叠编辑器 UI 网络封装或自动调度

## 2 阶段 A 实体分配器

实现 World 内的存活标记 代际数组 可回收编号集合 以及实体创建销毁

先不挂组件 让空实体创建 存活 销毁与编号复用独立成立

完成条件如下

- 创建两个实体 二者有效且编号不同
- 销毁第一个实体后 旧句柄立即失效
- 复用编号创建新实体时 代际不同 旧句柄不能访问新实体
- 两个 World 的编号可以相同 通过外部句柄传递时不会串世界
- 销毁一个实体不会破坏其他存活实体的身份

不要为了简化测试而一直递增编号且永不回收 那会绕开最值得验证的代际问题

## 3 阶段 B 组件存储

只实现一个 Position 存储和一个 Velocity 存储 每个存储使用 SparseList DenseEntityList DenseValueList Count

完成 Add Get Has Remove 与必要扩容 再让 World 记录实体拥有的组件类型

必须验证的关键路径如下

| 操作 | 观察结果 |
|---|---|
| 添加两个不同类型 | 它们属于同一 Entity 但可以位于不同组件池行号 |
| 删除中间行 | 末行填洞 被移动实体仍能得到自己的正确数据 |
| 删除末行 | 不会误改其他实体稀疏索引 |
| 扩容后重新 Get | 仍能读到正确值 |
| 删除最后一个组件 | 实体仍然存活 |
| 销毁实体 | 所有已附加组件都被移除 |

优先写能发现索引错位的测试 例如三个实体分别存不同坐标 删除中间实体后访问剩下两个

不要只测试 Count 变化 那无法证明索引映射正确

## 4 阶段 C Query 和 System

实现 All 与 None 条件 执行时选择最小必需组件池作为候选集

用四种实体验证查询 只有 Position 只有 Velocity 同时有二者 二者都有但被排除标签命中

查询 Position 与 Velocity 的结果应只包含符合全部条件且没有排除类型的实体

再写 MovementSystem 读取 Velocity 与逻辑步长 修改 Position

先通过普通控制台或无引擎测试工程运行 确保没有 UnityEngine 依赖

完成条件是多次推进后位置按预期改变 同时改变系统注册顺序能够解释数据读写变化

这里重点理解组件之间通过 Entity 关联 不是依赖不同数组的下标恰好一致

编辑器菜单 MmECS/验收阶段 D 固定 Tick 已在 Unity 通过 步长 0.5 时三次推进的 Tick 数为 0 1 2 位置为 0 0.5 1.5 阶段 C 回归仍为移动优先 1 改速优先 2 此项只验收固定步累计 不代表阶段 D 整体验收

2026-09-26 StructuralBuffer.Add<T> Remove<T> Destroy 已接入 Simulation.Tick 末尾 Unity 菜单 MmECS/验收阶段 D 结构提交已通过 验证遍历不漏项 同 Tick 后续系统仍见旧结构与已写字段 Tick 末移除 Remove 后 Add 的 FIFO 顺序以及 Destroy 后 Add 的非法顺序 阶段 C 与固定 Tick 回归通过

Simulation.Tick 在执行系统前调用 World.BeginSimulation World 的公开 Create Register 仅允许初始化阶段执行 Add Remove Destroy 复用单一操作体 只在初始化或内部结构提交阶段执行 缓冲回放由 World.CommitStructural 控制提交阶段 Unity 菜单 MmECS/验收阶段 D 入口保护已通过 验证首个 Tick 内及后续 Tick 外的公开入口拒绝即时修改 缓冲移除与销毁仍可提交 结构提交验收另检查异常后提交阶段关闭

World.Tick 已记录完整完成的逻辑 Tick 初值为 0 只在 Tick 末结构提交成功后递增 Unity 固定 Tick 菜单验收得到推进次数 0 1 2 对应已完成 Tick 0 1 3 结构提交异常时编号保持 0

MoveInput 已按目标 Tick 分桶提交 Simulation.Tick 在系统执行前冻结并消费目标 Tick 的输入 Unity 菜单 MmECS/验收阶段 D 输入队列已通过 验证乱序提交仍按 Tick 1 2 3 生效以及当前 Tick 冻结后的迟到输入被拒绝

业务 Command 队列 SpawnRequest 与 SpawnResult 以及表现输出尚未实现 后续仍按下述模拟步顺序扩展

建立一个固定顺序的模拟步

1. 取出目标 Tick 的输入和业务 Command
2. 执行本 Tick 的输入处理与业务系统
3. 消费按约定阶段产生的当 Tick 请求
4. 按入队顺序回放 StructuralBuffer
5. 形成表现输出 完成 Tick 编号推进 到达允许快照的边界

每个结构请求只在步骤 4 生效 当前 Tick 系统内不得即时改变查询结构

完成条件如下

- 循环中申请移除组件 当前查询不会漏遍历或重复遍历其他成员
- 移除操作在本 Tick 后续系统执行时尚未生效 下一 Tick 不再命中
- 修改已有 Health 字段 后续系统当 Tick 就能读到新血量
- 创建请求提交前不产生可被查询的实体 提交后完整初始组件已经齐全
- 通过 SpawnRequestId 能在下一 Tick 的 SpawnResult 中找到正式 Entity 结果在消费前被正确保存
- 多个结构请求按文档契约回放 非法顺序暴露调用错误
- 一次渲染前推进多个 Tick 不会让前几个 Tick 的表现事件被覆盖

这里要直接验证 FIFO 规则 不能借用 Arch 的缓冲后还声称维持原始操作顺序

## 6 阶段 E 一个完整业务切片

样例包含移动 输入一次攻击 伤害 死亡 血条与飘字 这足以检查大多数边界

### 6.1 数据与职责

| 数据或模块 | 职责 |
|---|---|
| Position 与 Velocity | 移动状态 |
| Health | 当前生命值和最大生命值 |
| Lifecycle | 已有字段 PendingDeath 表示本 Tick 后续业务需要跳过 |
| AttackCommand | 玩家希望向指定目标攻击的意图 |
| DamageRequest | 攻击规则验证后生成的伤害结算请求 |
| DamageSystem | 结算伤害 修改 Health 产出飘字所需值 |
| DeathSystem | 处理死亡规则 标记 PendingDeath 并排队销毁 |
| View Adapter | 读取血量 更新对象位置 播放飘字 对账实体存活情况 |

命令传入目标句柄不等于命令必然成功 攻击距离 冷却 目标是否有效等属于游戏规则 由模拟判断

### 6.2 UI 行为验收

先关闭角色信息面板 推进伤害 再打开面板 面板应显示当前血量

面板不能依赖自己关闭期间是否收到某条血量事件

在死亡 Tick 输出的飘字包含必要位置和数值 即使实体已销毁也能消费

UI 只保存展示所需的只读值和外部句柄 不持有 Storage 的可写数组或组件 ref

### 6.3 引擎适配验收

同一批输入先在无引擎模式运行 再在 Unity Adapter 驱动下运行 在相同模拟条件下比较结果

Unity 只负责收集输入 推进 Tick 和展示 核心测试不需要启动 Unity

如果接入了引擎物理 此比较必须使用相同的物理输入或独立物理实现 不把不同后端结果差异当作 ECS 存储错误

## 7 阶段 F 快照恢复

先实现同程序版本 同配置 同数学实现的内存快照 不直接承担跨版本存档

首版按组件类型复制所拥有的数据和映射 明确保存分配器 代际 空闲编号顺序 组件行顺序 World 单例 Tick 随机状态与未来请求

查询缓存和存储引用在恢复后重新绑定 表现层清理旧 Epoch 的待播事件并按恢复状态重新对账

禁止通过公开 Spawn 与 Add 逐个重放来假装精确恢复 原状态的编号回收顺序 行顺序和回调副作用可能因此变化

### 7.1 关键回放验证

1. 运行到 Tick K 在完成结构提交的边界保存快照
2. 记录快照完成之后才从外部提交的输入及其接纳时点 继续运行 M 个 Tick 得到模拟结果 A
3. 恢复 Tick K 的快照 按相同接纳时点重新提交上述新增输入并运行 M 个 Tick 得到结果 B
4. 比较 A 与 B 的实体身份 组件 单例 随机源及未来队列
5. 再创建和销毁实体 检查编号分配与代际也保持一致

K 和 M 是测试参数 不把某个固定数量写进框架逻辑

其中应包含一次随机决策 一次实体编号复用 一次组件中间行删除 未来 Tick 的命令以及尚未消费的 SpawnResult

快照中已经保存的未来输入不能再次投递 只重投快照完成之后新增的输入 命令和创建请求的序号分配器也应从快照状态继续

比较结果不能包含恢复时故意变化的宿主 StateEpoch 或 UI 对象引用

哈希可用于快速发现差异 定位错误仍需要能指出具体实体和字段的比较工具

此测试通过只证明所测运行条件下的恢复重演 不证明不同 CPU 平台 数学库或物理后端自动确定

## 8 阶段 G 性能与可观察性

先验证正确性 再测吞吐量 不用参考仓库 README 中的最快描述作为当前项目结论

### 8.1 基准至少区分这些工作负载

| 工作负载 | 主要观察 |
|---|---|
| 单组件顺序读取与写入 | 组件数据遍历成本 |
| 多组件交集查询 | 稀疏索引检查与匹配比例 |
| 高频 Add Remove Destroy | 结构提交 数据搬移与编号管理 |
| 随机 Entity 访问 | 索引访问与缓存局部性 |
| 快照保存恢复 | 状态体积 复制耗时与峰值内存 |
| View 投影与事件消费 | 核心以外的转换和展示成本 |

使用可配置实体数量 组件组合 变化比例与查询次数 记录预热和测量条件

分别测冷启动 扩容阶段与预分配后的稳态 预热并排除日志 IO 和测试数据构造

至少记录平均耗时 高分位耗时 GC 分配和内存占用 在目标运行时测量

编辑器运行与 IL2CPP 构建结果可能不同 不把桌面 .NET 成绩直接当作手机目标预算

### 8.2 优化触发条件

- 类型检查占比明显时 再研究增量 Filter 或更专用的查询
- 紧密遍历仍是主要成本且实体结构相对稳定时 再评估 Archetype 原型
- 结构变化占比高时 优先测搬移 数据粒度和请求合并 不先加线程
- 结构命令分配占比明显时 再测无装箱的结构体命令布局 同时保留跨操作类型的 FIFO 顺序
- 确实存在多个独立的大批量任务时 才研究读写声明 冲突分析与 Job 调度
- 快照成为瓶颈时 再测分块复制 脏页或差量存储

优化依据应是当前游戏数据 不是为了让实现看上去像某个成熟框架

### 8.3 最小调试能力

先提供文本形式的实体与组件枚举 系统执行顺序 每 Tick 请求和事件数量 快照差异报告

发现问题时能够回答 哪个 Tick 哪个系统修改了哪个实体的哪个字段

Unity 可视化 Inspector 可以以后加 它不应该成为理解世界状态的唯一渠道
